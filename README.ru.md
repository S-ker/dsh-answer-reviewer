# dsh-answer-reviewer

Плагин для хоста dsh: каждый раз, когда агент собирается закрыть ход (turn),
плагин извлекает финальный текст ассистента, адресованный пользователю, и
просит отдельную модель-рецензента оценить его по шкале 1–100. Если оценка
ниже заданного порога `threshold` (по умолчанию `80`), плагин возвращает
агента обратно в тот же ход с одним-единственным самым важным замечанием
рецензента в качестве конкретной обратной связи. После того как ход был
возвращён на доработку `maxChallenges` раз (по умолчанию `5`), ответ агента
разрешается закрыть ход как есть — предел является защитой от утечки, а не
настоящим шлюзом; настоящий шлюз — это порог оценки.

Настройте шлюз, включите/выключите рецензента, измените предел возвратов на
доработку или выберите отдельную модель-рецензента — всё в реальном времени,
без перезапуска хоста — через **вкладку Reviewer 配置** в кольце видов
беседы над композером, через дополнительную вкладку боковой панели, через
самостоятельный конфигурационный интерфейс на **`http://127.0.0.1:3987`**
или через тот же JSON API из `curl`. Затем каждый проверенный ответ
показывает собственный **бейдж оценки** в строке действий сообщения
(см. [Бейдж оценки](#бейдж-оценки-с-070)). Конфигурация на диске лежит в
`~/.dsh/answer-reviewer.json` (переопределите с помощью `REVIEWER_CONFIG_PATH`);
если файл отсутствует, ходы хоста проходят с настройками по умолчанию.

Модель-рецензент видит **каждый настоящий пользовательский промпт**, который
пользователь выдал в сессии (любое событие `user/message`, у которого
`source.kind` не равно `'plugin'`), помеченный как `<all_user_prompts>`, плюс
финальный ответ ассистента под `<reply>`. Контекст, внедрённый плагином
(уведомления об изменении файлов, AGENTS.md, содержимое навыков, системные
напоминания), отфильтровывается, чтобы рецензент оценивал именно то, что
пользователь спросил, а не контекст, который харнесс несёт в этот момент.

Модель-рецензент независима от рабочей модели агента, когда заданы
`reviewProvider` / `reviewModel`; в противном случае плагин использует текущий
маршрут агента, поэтому работает «из коробки».

Оценка — это не только внутренний шлюз — она **показывается на ответе,
который оценила**:

```
  ⤷  ⧉  ↻  👍  👎   ● 评分 92        ← в строке действий сообщения
```

> **Русская локализация (добавлена в этом форке):** интерфейс поддерживает
> два языка — китайский (исходный) и русский. Язык выбирается автоматически
> по локали браузера (русский браузер → русские подписи) либо переключается
> вручную ссылкой в шапке страницы `http://127.0.0.1:3987`.

## Бейдж оценки (с 0.7.0)

Каждое финализированное сообщение ассистента несёт оценку, которую дал ему
рецензент, в виде небольшого цветного бейджа в строке действий сообщения,
рядом со стандартными кнопками копирования/повтора и «Нравится/Не нравится»:

| Вердикт | Бейдж | Значение |
| --- | --- | --- |
| Прошёл шлюз | `● 评分 92` на зелёном фоне | `score >= threshold`; ход закрылся с первого взгляда |
| Ниже шлюза | `● 评分 61 · 第2次` на янтарном фоне | Возврат на доработку; число в бейдже — попытка, которая в итоге засчиталась |
| Попытки исчерпаны | `● 评分 55 · 第4次` на янтарном фоне | Всё ещё ниже шлюза, а `maxChallenges` исчерпан, поэтому ничего не возвращалось (с 0.7.1) |

Наведите курсор на бейдж, чтобы увидеть шлюз, вердикт и собственную причину
рецензента:

```
阈值 80 · 通过 · 第 4 轮
Ответ ответил на вопрос, но так и не назвал проблемный файл.
```

Замечания по дизайну:

- **Привязывается к ответу, а не к ходу.** Оценка записывается под тем же
  устойчивым идентификатором сообщения, который оболочка передаёт в строку
  действий (`assistant/message` → `data.message.id`), поэтому бейдж и шлюз
  никогда не могут разойтись во мнении о том, к какому ответу относится
  оценка.
- **Не рендерит ничего, когда оценки нет.** Отключённый плагин, отсутствующий
  маршрут рецензирования, неразбираемый ответ или исчерпанный предел повторов
  оставляют строку байт-в-байт такой же, как в стандартном dsh — без
  заглушки, спиннера и зарезервированного места.
- **Повторы видны.** Ход, возвращённый на доработку, показывает `第2次` на
  ответе, который в итоге прошёл, поэтому успешная оценка с третьей попытки
  не читается как успех с первой. Провальный промежуточный ответ сохраняет
  собственный бейдж, если он у него есть.
- **Последний ответ всегда несёт бейдж.** Предел повторов заставляет замолчать
  *возврат на доработку*, но никогда не рецензирование — ход, у которого
  `maxChallenges` закончился, всё равно публикует итоговую оценку с пометкой
  `capped`. Иначе ответ, который пользователь реально читает, был бы
  единственным ответом без оценки (исправлено в 0.7.1).
- **Цвета — хоста.** Бейдж использует собственные токены dsh
  `--dsw-alias-state-success-*` / `--dsw-alias-state-warn-*`, поэтому следует
  активной теме без локальной палитры.

### Лента оценок

Бейдж читает JSON-ленту с того же origin, которую хост монтирует на своём
собственном веб-сервере:

```
GET /api/dsh-answer-reviewer/reviews   →   { entries: [...], at }
```

Каждая запись — `{ messageId, score, threshold, decision, attempt, turn, reason, at }`,
новые сверху, максимум 200 последних оценок. Она регистрируется через
`ctx.webServer.register(...)` хоста и защищается забором соединений композиции
(проверка Host/Origin плюс cookie токена входа), поэтому страница может читать
её без ослабления CORS. Вспомогательный сервис `127.0.0.1:3987` намеренно
**не** предоставляет кросс-доменное чтение — иначе любой сайт, который
посещает пользователь, мог бы читать и переписывать его конфигурацию
рецензента — но он зеркалит ту же полезную нагрузку по `/api/reviews` для
`curl`.

## Зачем отдельная модель?

Модель-рецензент использует строгий промпт-оценщик, возвращающий только JSON
(`{score, reason}`), который агент никогда не видит напрямую. Замечания
внедряются обратно как `user/message` с `source: { kind: 'plugin', plugin:
'dsh-answer-reviewer' }`, поэтому агент воспринимает их как пользовательский
ввод — но агенту явно сказано не упоминать рецензию пользователю. Другой
провайдер/модель снижает вероятность того, что самопроверенная оценка
«проштампует» собственную работу, а явный числовой шлюз означает, что хорошо
настроенная модель, возвращающая 80+, не запустит никакой повторной попытки.

## Живая конфигурация (с 0.4.0)

Плагин запускает крошечный `node:http`-сервер, привязанный к `127.0.0.1:3987`
(без внешнего доступа). Откройте его в браузере, чтобы увидеть форму, путь к
файлу конфигурации на диске и скользящий список последних 15 результатов
рецензирования. Тот же JSON API доступен из оболочки:

```bash
# Прочитать текущую действующую конфигурацию + переопределения + путь к файлу
curl -s http://127.0.0.1:3987/api/config

# Подправить порог (записываются только те поля, что вы POST-ите)
curl -s -X POST http://127.0.0.1:3987/api/config \
  -H 'content-type: application/json' \
  -d '{"threshold": 90}'

# Отключить рецензента
curl -s -X POST http://127.0.0.1:3987/api/config \
  -H 'content-type: application/json' \
  -d '{"enabled": false}'

# Стереть переопределения к значениям по умолчанию (также удаляет файл на диске)
curl -s -X DELETE http://127.0.0.1:3987/api/config

# Посмотреть последние 20 результатов рецензирования
curl -s http://127.0.0.1:3987/api/recent

# Посмотреть оценку каждого последнего ответа ассистента по id сообщения
curl -s http://127.0.0.1:3987/api/reviews
```

Отключите сервер с помощью `REVIEWER_HTTP=0`. Измените порт с помощью
`REVIEWER_HTTP_PORT=<n>`. Переместите файл на диске с помощью
`REVIEWER_CONFIG_PATH=<abs path>`. Следующий ход подхватит новое значение без
перезапуска хоста.

## Вкладка конфигурации (с 0.7.6)

Плагин регистрирует полноценную вкладку в слот `conversation.view` оболочки —
то же кольцо, что несёт собственные вкладки dsh `对话 / 轨迹 / 记忆系统` над
композером:

```
  对话 │ 轨迹 │ 记忆系统 │ Reviewer 配置
                          ╰──────────── активна → основная область — это страница
```

Нажмите на вкладку, и страница конфигурации займёт область беседы, точно как
любой другой вид беседы:

```
┌────────────────────────────────────────────────────────┐
│  dsh-answer-reviewer · 实时配置   新标签打开  127.0.0.1:3987 │
├────────────────────────────────────────────────────────┤
│                                                        │
│              (форма конфигурации, в iframe)            │
│                                                        │
└────────────────────────────────────────────────────────┘
```

Три продуманных момента дизайна:

- **Это настоящий вид, а не полоса над композером.** Вкладка регистрируется
  с `order: 40`, поэтому попадает после всех штатных видов (чат `0`,
  траектория `10`, мнемоника `30`). dsh рендерит зарегистрированный вид только
  пока это *активная* вкладка, поэтому переключение размонтирует iframe, и его
  таймеры опроса останавливаются сами — без пропа `visible`, без сохранённого
  состояния «открыто/закрыто».
- **Без контроля сворачивания и без оверлея.** У вкладки нет «открыто» и
  «закрыто»; область вида *и есть* страница. Это устраняет всю старую
  геометрическую проблему дока (наложение вместо выталкивания колонки
  композера фиксированной высоты) в самом источнике.
- **Мёртвый конфигурационный сервер получает подсказку, а не пустой кадр.**
  Вид опрашивает `/api/health` один раз при монтировании; если вспомогательный
  сервис не работает (например, `REVIEWER_HTTP=0`), он заменяет кадр
  информативным сообщением с указанием на порт и лог хоста.

Это **основная** поверхность: ей нужен только базовый клиентский сервис
`slots`, поэтому она доступна в любой установке — `dsh-better-sidebar` не
требуется.

Вкладка, вкладка боковой панели и отдельная страница встраивают **один и тот
же** URL. Сохранение через любую из них видно остальным на самом следующем
GET, потому что все три читают единственный `ConfigStore`, живущий в процессе
хоста.

## Боковая карточка (с 0.5.0)

Если профиль хоста также устанавливает
[`dsh-better-sidebar`](https://dshfind.com/en/plugins/omdsh-dev/DSH-better-sidebar),
плагин дополнительно регистрирует вкладку правой боковой панели с названием
**«Reviewer 配置»**. Откройте её из меню `+` боковой панели (рядом с Файлы /
Терминал / Браузер). Содержимое вкладки — та же форма, что и у отдельного
сервера, загруженная внутри iframe — сохранение значения через вкладку видно
отдельному серверу (и наоборот) на самом следующем GET. Когда вкладка не
активна, iframe размонтируется, чтобы фоновые вкладки не продолжали опрос.

Если `dsh-better-sidebar` не установлен, боковая карточка просто скрыта —
вкладка конфигурации и отдельная страница `127.0.0.1:3987` по-прежнему
охватывают вас. Каждая поверхность необязательна, и плагин работает без всех
них.

Зависимость от better-sidebar **мягкая, по замыслу**: вкладка ожидается лениво
(`ctx.inject(["betterSidebar"], …)`), а не объявляется в `exports.inject`.
Жёсткий inject оставил бы клиентскую запись в состоянии
`pending (waiting for service: betterSidebar)` на любом хосте без
dsh-better-sidebar, что аудит загрузки веб-версии сообщает как
`web boot: 1 entry did not activate`, а оболочка рендерит как баннер
**«Failed to load plugins»** над всей главной страницей. См. запись в
журнале изменений 0.5.3.

## Установка

Добавьте пакет в `dependencies` вашего профиля и в `dsh.profile.bundles`,
затем обновите хост.

```jsonc
// ~/.dsh/profiles/web/package.json
{
  "dependencies": {
    "dsh-answer-reviewer": "file:/Users/bycall/Downloads/workbuddy/Claw/dsh-answer-reviewer"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "dsh-answer-reviewer"
      ]
    }
  }
}
```

Затем `dsh plugin --profile web install` и перезапустите хост.

## Конфигурация

| ключ              | тип      | по умолчанию | значение                                                       |
| ----------------- | --------- | ------- | ---------------------------------------------------------------- |
| `enabled`         | `boolean` | `true`  | Общий выключатель. Установите `false`, чтобы отключить без удаления. |
| `threshold`       | `number`  | `80`    | Инклюзивный шлюз оценки 1–100. Ниже — плагин возвращает на доработку. |
| `maxChallenges`   | `number`  | `5`     | Жёсткий предел возвратов на (сессия, ход). Жёстко ограничен `8`.      |
| `maxReviewTokens` | `number`  | `512`   | Ограничение вывода модели-рецензента.                                 |
| `timeoutMs`       | `number`  | `60000` | Ограничение реального времени вызова рецензирования.               |
| `reviewProvider`  | `string`  | агента  | Провайдер для выделенной модели-рецензента. Должен сочетаться с моделью.   |
| `reviewModel`     | `string`  | агента  | Идентификатор модели для выделенной модели-рецензента. Должен сочетаться с провайдером. |

`threshold` должен быть целым числом в `[1, 100]`; значения вне диапазона
откатываются к значению по умолчанию, а не молча ограничиваются (поэтому
неправильно заданная конфигурация не меняет тихо шлюз с «80» на «100»).

`reviewProvider` и `reviewModel` должны задаваться вместе; задание одного без
другого — ошибка конфигурации, и плагин откажется монтироваться.

## Поведение

- **Ходы субагентов пропускаются.** Плагин рецензирует только
  пользовательского агента. `agent.session.header.origin === 'subagent'`
  отфильтровывается.
- **Пустой / прерванный вывод ассистента пропускается.** Нет рецензии — нет
  возврата на доработку.
- **Сбои вызова рецензии открыты (fail-open).** Ошибки сети, тайм-ауты, сбои
  разбора или ошибки на стороне модели — всё логирует предупреждение и даёт
  ходу закрыться нормально. Нестабильный рецензент никогда не должен
  заклинивать хост.
- **Сигналы прерывания обрывают всё.** Если пользователь поставил на паузу или
  отменил ход, рецензия отменяется на полпути, и ход остаётся в покое.
- **Оценки вне диапазона закрываются (fail-closed).** Модель-рецензент должна
  вернуть целое число в `[1, 100]` с непустым `reason`. Всё остальное (модель
  возвращает «1.5», «99.9%», «I score this ...» и т. п.) считается сбоем
  разбора — открытие дало бы сбойной модели купить проход, вернув мусор.
- **Счётчик на ход ограничен.** После того как ход возвращался на доработку
  `maxChallenges` раз, последующие границы хода внутри того же хода могут
  закрыться без рецензии. С значением по умолчанию `5` вы увидите максимум
  пять повторных попыток с возвратом, прежде чем ответ агента уйдёт
  пользователю как есть, даже если модель-рецензент всё ещё оценивает его ниже
  порога — предел это жёсткий бюджет, а не мягкая подсказка.
- **Агенту сказано не упоминать рецензию.** Сообщение возврата явно
  инструктирует агента устранить замечание молча.

## Тест

```
node test/smoke.mjs
```

Смоук-тест проверяет каждый чистый помощник, а также ветви
fail-open, пропуска субагента, ниже порога и исчерпания предела в
`onTurnStopping` с помощью мок-объектов (моки потоковых чанков в форме
`BlockAssembler`). Он не запускает хост dsh.

## Файлы

- `lib/index.js` — cordis `apply`, подключает слушатель и оркеструет вызов
  рецензии. Импортирует из `./internal.js`.
- `lib/internal.js` — повторный экспорт-бочка, чтобы `lib/index.js` и тесты
  импортировали из одного места.
- `lib/review.js` — чистые помощники: `resolveConfig`, `extractAssistantText`,
  `extractUserPrompts`, `buildReviewPrompt`, `parseScore`,
  `isScoreAcceptable`, `buildSteerMessage`, `createChallengeCounter`
  и публичная zod-схема `Config`.
- `lib/config-store.js` — `createConfigStore` (постоянный, горячо
  перезагружаемый), `defaultConfigPath`, константы env-переменных для
  HTTP-сервера.
- `lib/server.js` — `startServer(store, opts)` — только для `127.0.0.1`
  экземпляр `node:http` (HTML-форма + JSON API). Поддерживает русский язык
  интерфейса.
- `lib/client.js` — клиентский бандл `window.__ModuleLoader__.load`.
  Регистрирует бейдж оценки и вкладку `Reviewer 配置` в слоты оболочки
  `conversation.chat.assistant-actions` / `conversation.view`; когда профиль
  хоста также включает `dsh-better-sidebar`, регистрирует и боковую карточку
  «Reviewer 配置». Оба монтирования необязательны, и запись активируется без
  них.
- `cordis.patch.yml` — запись бандла cordis, монтирующая плагин.
- `test/smoke.mjs` — смоук-тест на node ESM (58 случаев).

## Примечания этого форка

- **Русская локализация.** Интерфейс (отдельная страница `127.0.0.1:3987`,
  вкладка конфигурации, боковая карточка и бейдж оценки) теперь поддерживает
  русский как второй язык. Русский браузер автоматически получает русские
  подписи; на странице `http://127.0.0.1:3987` язык можно переключить
  вручную. Китайский остаётся языком по умолчанию.
- **Совместимость с DSH 0.2.x (формат сессии v4).** В исходном `lib/review.js`
  обе внедрённые модели-сообщения использовали устаревшую обёртку
  `{ kind: 'plugin', plugin: ... }`, которую формат v4 отклоняет
  (`format v4 message requires a producer-owned source kind`), из-за чего
  возврат на доработку прерывал весь ход. В этом форке сообщения используют
  producer-owned вид `{ kind: 'dsh-answer-reviewer', ... }`, а
  `extractUserPrompts()` принимает и v4-форму (сообщение прямо на `data`),
  и v3-форму (под `data.message`), поэтому `<all_user_prompts>` снова
  наполняется на 0.2.x.
